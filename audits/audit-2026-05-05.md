## Cross-Cutting Issues

These are individual bugs that don't fit cleanly under a single area, or that span multiple files. Listed by severity.

### C-1. Convergence flag stored with inverted semantics (Critical)

**File:** `python/lsst/meas/extensions/scarlet/scarletDeblendTask.py:1424,1461,1685`, schema declared at `:861-865`

`_checkBlendConvergence` returns `True` when the blend *converged*. That value flows into `_updateParentRecord(... converged=...)`, which writes it verbatim into the schema field `deblend_blendConvergenceFailedFlag`:

```python
parentRecord.set("deblend_blendConvergenceFailedFlag", converged)  # :1685
```

A successful blend is therefore flagged as having failed convergence, and a non-converged blend is flagged as success. Same inversion applies to `_skipBlend` (passes `converged=False` for skipped blends → flag stored as `False`, i.e. "not failed"), and to `_addIsolatedSource` which passes `converged=True` for sources that were never even fit. This affects every catalog produced by the task.

**Fix:** Either pass `not converged` at the three call sites, or rename the schema field to `deblend_blendConverged` and flip the semantics consistently. The latter is cleaner but is a schema-breaking change.

**Developer comment (2026-05-22):** Kept the field name; renamed the `_updateParentRecord` parameter to `convergenceFailed`. Skipped, isolated, and all-failed parents report `False` (never fit), so the flag fires only for a fitted blend that did not converge.

### C-2. `updateCatalogFootprints` returns `NoWorkFound(...)` instead of raising (Critical)

**File:** `python/lsst/meas/extensions/scarlet/io/utils.py:182`

```python
if not modelData.blends and not modelData.isolated:
    return NoWorkFound("Scarlet model data is empty")
```

`NoWorkFound` is a control-flow exception in `lsst.pipe.base` — the intent is to short-circuit a pipeline quantum when the input has no work. As written, the function returns the exception *as a value* from a function whose return annotation is `None`, and the empty-input case silently slips past every caller. Line 193 in the same file uses `raise NoWorkFound(...)` correctly, so this is a typo, not a deliberate API change.

**Fix:** `raise NoWorkFound("Scarlet model data is empty")`.

### C-3. `except ValueError` should be `except KeyError` in legacy-zip fallback (Critical)

**File:** `python/lsst/meas/extensions/scarlet/io/utils.py:509`

```python
try:
    metadata = from_json(zip_file.open('metadata').read())
except ValueError:
    # File is in legacy format, fall back to top-level psf/psf_shape
    filenames += ['psf', 'psf_shape']
```

`ZipFile.open` raises `KeyError` (not `ValueError`) when the entry is absent. The legacy-format fallback path is therefore unreachable: legacy-format files crash during the `from_json` step or earlier with an uncaught `KeyError`, never reaching the `psf`/`psf_shape` recovery. Reading old-format archives (the very purpose of this branch) is silently broken.

The next try/except on line 513 catches `KeyError` correctly, which makes the inconsistency more confusing.

**Fix:** `except KeyError:`.

### C-4. `detectedPeak` indexed in unfiltered list while `peaks` is the filtered list (Critical)

**File:** `python/lsst/meas/extensions/scarlet/scarletDeblendTask.py:413-420`

In `deblend()`, the peak list is filtered to drop pseudo-source peaks:

```python
peaks = [peak for peak in footprint.peaks if not isPseudoSource(peak, ...)]
```

Sources are then constructed in 1:1 correspondence with the filtered `peaks`. But the back-pointer to the `PeakRecord` is written using the *unfiltered* index:

```python
sources[k].detectedPeak = footprint.peaks[k]
```

Whenever a pseudo-peak appears at index `≤ k` in the unfiltered list, `sources[k]` gets the wrong PeakRecord. Downstream `_addDeblendedSource(peak=scarletSource.detectedPeak)` then writes the wrong `deblend_peak_center_x/y`, the wrong `deblend_peakId`, and copies the wrong peak schema fields into the deblended source record. The misalignment check on line 415 happens to be computed against the right peak (`peaks[k]`) and silently agrees with itself.

**Fix:** Build `non_pseudo_peaks = [p for p in footprint.peaks if not isPseudoSource(...)]` and use `non_pseudo_peaks[k]` for `detectedPeak`. (`peaks` and `non_pseudo_peaks` may collapse into one list once the misalignment check is rewritten.)

### C-5. Aggregate update writes to wrong record when all sub-blends fail (Critical)

**File:** `python/lsst/meas/extensions/scarlet/scarletDeblendTask.py:1279-1293`

```python
for blendRecord in blendRecords:
    try:
        blend = self._deblendParent(...)
        ...
    except DeblenderError:
        self._skipBlend(...)
        continue
...
if len(parentBlends) == 0:
    self._updateParentRecord(parentRecord=blendRecord, ...)
```

By the time control reaches the `if len(parentBlends) == 0:` block, `blendRecord` is the loop variable from the last iteration of the `for` loop — a sub-blend record, not the top-level parent. The "all sub-blends failed" summary is therefore written onto the last sub-blend's record (which `_skipBlend` already populated), and the actual top-level parent record is left in default state. Net effect: parents whose every sub-blend failed have no aggregate flags, no nChild, no chi², and no skip reason at the parent level.

**Fix:** `parentRecord=parentRecord` (the outer `parentRecord` is still in scope).

### C-6. `computeNearestPsfMultiBand` overwrites caller's `psfCenter` mid-loop (Critical)

**File:** `python/lsst/meas/extensions/scarlet/utils.py:236-241`

```python
for b, exposure in enumerate(mExposure):
    psf, psfCenter, _ = computeNearestPsf(catalog, exposure, psfCenter, ...)
    ...
```

`psfCenter` is reassigned every iteration. Each band's nearest-PSF search starts from the *previous band's fallback location*, not the original requested center. If band 0's PSF is invalid at the original center but happens to be valid 50 px away, band 1 will then search from that 50-px-away location — and might in turn fall back somewhere else. The resulting "multiband PSF" therefore mixes per-band PSFs sampled at different sky points, which breaks the implicit assumption that channels of the multiband PSF share an aligned center.

Combined with U-1 (which projects per-band PSFs onto the union bbox), the assembled multiband PSF on a recovery path can be silently mis-registered between bands. This is the kind of bug that produces small but consistent astrometric biases in the deblended catalog.

**Fix:** Keep the original requested center in a separate local: `searchCenter = psfCenter; for b, exposure in ...: psf, fallbackCenter, _ = computeNearestPsf(catalog, exposure, searchCenter, ...)`. Decide separately what to do when bands disagree on fallback (refuse? warn?).

**Developer comment (2026-05-26):** Rewrote `computeNearestPsfMultiBand` to (1) try the requested center in every band, (2) on failure, find a single common fallback location for the failing bands and upgrade every band to it when that location is also valid for the bands that succeeded at the center, (3) fall back per band only when no common location exists, logging a warning whenever the kept bands end up at more than one location. Also closes U-1.

### C-7. Schema-version safety net is broken (High)

**File:** `python/lsst/meas/extensions/scarlet/io/model_data.py:40-52`

```python
if scl.io.model_data.CURRENT_SCHEMA != SCARLET_LITE_SCHEMA:
    scarletVersion = SCARLET_LITE_SCHEMA.split("."), scl.io.model_data.CURRENT_SCHEMA.split(".")
    ...
    if int(scarletVersion[0]) > int(lsstVersion[0]):
        raise RuntimeError(...)
```

The trailing comma on line 40 packs `scarletVersion` into a 2-tuple of lists. `scarletVersion[0]` is then `["1","0","0"]`, and `int(scarletVersion[0])` raises `TypeError: int() argument must be a string... not 'list'`. The whole branch is dormant in the current build (the outer `!=` test is False), so this is a latent failure — but it is the very mechanism designed to detect the case it was written to handle. The day scarlet_lite bumps its schema, the user gets a confusing `TypeError` instead of the helpful `RuntimeError`.

**Fix:** Drop the trailing comma. Better: replace the whole hand-rolled comparison with `packaging.version.Version` or tuple-of-ints comparison.

**Developer comment (2026-05-26):** Bidirectional drift guard instead of the audit's forward-only check. An older installed scarlet may not emit the keys this package's IO layer expects, so it's as much a drift as a newer one and should also raise.

### C-9. `IndexError` is unreachable for negative pixel coordinates (High)

**File:** `python/lsst/meas/extensions/scarlet/scarletDeblendTask.py:1796-1801`

```python
x = peak["i_x"] - xmin
y = peak["i_y"] - ymin
try:
    footprintImage.data[y, x] - 1
except IndexError:
    raise RuntimeError(...)
```

NumPy raises `IndexError` only for positive out-of-range indices; negative indices silently wrap from the end of the array. A peak west or south of `(xmin, ymin)` reads the value of an unrelated pixel on the opposite edge and proceeds without error.

**Fix:**
```python
if x < 0 or y < 0 or y >= footprintImage.data.shape[0] or x >= footprintImage.data.shape[1]:
    raise RuntimeError(...)
```

### C-11. NaN poisoning of `loss` in deconvolution iteration (High)

**File:** `python/lsst/meas/extensions/scarlet/deconvolveExposureTask.py:341-346`

```python
residual = observation.images - observation.convolve(model)
loss.append(-0.5 * np.sum(residual.data**2))
update = observation.convolve(residual, grad=True)
update.data[:] *= step
model += update
model.data[(model.data < 0) | ~np.isfinite(model.data)] = 0
```

The NaN/Inf cleanup on the last line happens *after* the loss has been recorded and *after* the convergence test will run on the next iteration. If `model.data` ever contains a NaN at the start of an iteration (one bad FFT, one degenerate input), every value cascades:

- `observation.convolve(model)` produces NaN everywhere.
- `residual` is NaN everywhere.
- `np.sum(residual**2)` is NaN, recorded into `loss`.
- The convergence test `np.abs(loss[-1] - loss[-2]) < eRel * np.abs(loss[-1])` evaluates to `False` (NaN comparisons return False), so the loop keeps running.
- The divergence test `loss[-1] < loss[-2]` also evaluates to `False`, so the step is never halved.

Iteration runs to `maxIter` on garbage. Recent commit `1603f70` ("Make deconvolution more robust against non-finite values") cleans `model` at the end of the iteration, but does not defend `loss` or short-circuit on `~np.isfinite(loss[-1])`. Also: the variance plane is never sanitized in `_buildObservation`, so `noise_rms` can still go non-finite for pathological inputs (`calculate_update_step` correctly handles that case, but downstream consumers inherit a possibly-NaN variance plane via C-12).

**Fix:** Sanitize `model` and/or `residual.data` *before* recording the loss; add `if not np.isfinite(loss[-1]): break` (or restart with a smaller step) after the append.

### C-12. Output exposure shares mask/variance by reference; variance is not propagated (High)

**File:** `python/lsst/meas/extensions/scarlet/deconvolveExposureTask.py:372-389`

```python
image = afwImage.Image(array=model, xy0=..., deep=False, dtype=...)
maskedImage = afwImage.MaskedImage(image=image, mask=coadd.mask, variance=coadd.variance, dtype=...)
```

Two related problems:

1. **Reference sharing.** With `deep=False` and `mask=coadd.mask`/`variance=coadd.variance`, the output `Exposure` shares its mask and variance planes with the input coadd. Downstream tasks that mutate the deconvolved exposure's mask/variance will silently mutate the input.

2. **Variance is not the variance of the deconvolved model.** The output exposure carries the input coadd's variance, but convolution-then-deconvolution changes pixel covariance — the variance plane no longer corresponds to the pixel values it accompanies. Detection or measurement run on this exposure will under-estimate noise wherever the deconvolution sharpened features, and over-estimate it elsewhere. This is presented to consumers as if it were the variance of the deconvolved model.

**Fix:** Deep-copy the mask and (a placeholder for) variance, and either compute a propagated variance plane through the deconvolution operator or set a `BAD_VARIANCE` mask bit / clear the variance plane and document that downstream consumers must supply their own variance.

### C-13. Multi-peak parent with no intersecting deconvolved footprint silently disappears (High)

**File:** `python/lsst/meas/extensions/scarlet/scarletDeblendTask.py:1204-1209,1731-1746`

In `_initializeCatalogs`, only single-peak parents are added to the `isolated` list. Multi-peak parents go through `_buildIntersectingFootprints`, which only emits a `blendRecord` if the deconvolved footprint *intersects* at least one peak (`if len(intersection.peaks) > 0`). If no intersection exists (e.g. very faint parent that didn't survive `minDeconvolvedArea`), zero `blendRecords` are added.

In the main loop, `len(blendRecords) == 0 → continue` (with `processSingles=False`), and the parent record is left at default for *every* `deblend_*` field — no `deblend_skipped` flag, no `deblend_nChild`, no chi², no skip reason. The parent is silently lost.

**Fix:** Either always emit at least one blendRecord (even one equal to the parent footprint) so the main loop has a record to skip, or detect the empty case and call `_skipBlend(...)` with a new sub-flag like `deblend_skipped_noDeconvolved`.

### IO-1. Peak read/write type asymmetry (`float` write, `int` read) (High)

**File:** `python/lsst/meas/extensions/scarlet/io/source_data.py:80,110`

```python
# as_dict (write):
"peak": tuple(float(p) for p in self.peak),
# from_dict (read):
peak = tuple(int(p) for p in data["peak"])
```

The dataclass field is annotated `tuple[int, int]` and `IsolatedSource.from_footprint` (`source.py:100`) reads from `getIy/getIx` which return ints, so peaks are integers in practice. But the float-on-write / int-on-read pair will silently truncate any sub-pixel peak that ever reaches this path — and on negative values, `int()` floors *toward zero* rather than down, so the truncation is asymmetric.

**Fix:** Pick one. Either peaks are integers (write `int(p)` too, drop the float cast) or peaks are floats (annotate `tuple[float, float]`, drop the int cast on read).

### IO-2. `monochromaticDataToScarlet` peak ordering inconsistent across branches (High)

**File:** `python/lsst/meas/extensions/scarlet/io/utils.py:114,128`

In the "component" branch:
```python

```
In the "factorized" branch:

### DC-1. Step halving keeps the diverging update (High)

**File:** `python/lsst/meas/extensions/scarlet/deconvolveExposureTask.py:354-356`

```python
if len(loss) > 1 and loss[-1] < loss[-2]:
    step = step / 2
    self.log.warning(f"Loss increased at iteration {n}, decreasing scale to {step}")
```

(See also C-11 for the loss-sign discussion.) When divergence is detected, `step` is halved for *future* iterations, but `model += update` already happened with the bad step on the previous line. There's no rollback. The diverging update is permanent in `model`. Downstream NaN cleanup at line 346 just clamps NaN→0 inside the bad model, then the next iteration tries to recover from a corrupted state.

**Fix:** Save `prev_model = model.data.copy()` before applying the update; if the loss increased, restore `model.data[:] = prev_model` and retry with the halved step. Standard line-search / backtracking pattern.

**Developer comment (2026-05-21):** Empirically observed while writing `test_deconvolve_one_isolated_psf`: on a single isolated PSF source, the deconvolver leaves a per-pixel residual at the source peak of ~10σ of noise. Tightening convergence makes it **worse**, not better — `maxIter=100, eRel=1e-3` (defaults) gives ~9.9σ peak residual; `maxIter=1000, eRel=1e-6` gives ~11.5σ; `maxIter=5000, eRel=1e-8` gives ~14σ. The monotonic degradation with iteration count is consistent with this finding (bad updates accumulating without rollback) and possibly DC-3 (footprint oscillation) and DC-4 (step decay). Total flux over the source's 5×5 support is conserved within 1σ regardless of convergence settings, so the issue is flux redistribution between adjacent pixels, not flux loss. The Phase 1 test (`test_deconvolve_one_isolated_psf`) was reframed to test flux conservation rather than per-pixel recovery; if a fix lands here (or in DC-3 / DC-4) the test can be tightened to pixel-level. If none of the audit fixes resolve it, open a separate ticket to investigate.

### DC-3. Footprint multiplication oscillates against gradient pushes (Medium)

**File:** `python/lsst/meas/extensions/scarlet/deconvolveExposureTask.py:336-351`

The loop applies a footprint mask after each gradient step:
```python
update = observation.convolve(residual, grad=True)
update.data[:] *= step
model += update
model.data[:] *= footprintImage   # mask outside footprint
```

The gradient continually pushes flux outside the footprint, the multiplication zeros it back, and the loss is then computed on the unrestricted residual at the start of the next iteration. The result is oscillation around the footprint boundary instead of monotone descent. Tight footprints make this worse; many runs probably hit `maxIter` not because the fit is hard but because the loss can never decrease past the footprint-boundary flux that gets erased every step.

**Fix:** Either zero the *gradient* outside the footprint (so the model never wanders out in the first place), or include the footprint mask in the residual computation so the loss is consistent with the model.

**Developer comment:** This is a great catch but this should probably be deferred to a future ticket because this is an algorithmic change. I think we should actually do both, zero the model outside of the footprints initially *and* zero the gradients, although I have to think about this more deeply to understand whether or not there will really be a difference.

### DC-4. Step never recovers after halving (Medium)

**File:** `python/lsst/meas/extensions/scarlet/deconvolveExposureTask.py:354-356`

After one bad iteration, `step` is halved permanently. Long noisy runs halve and halve until `step` is microscopic, at which point the convergence test on `|loss[-1] - loss[-2]| < eRel * |loss[-1]|` is trivially satisfied for noise reasons regardless of fit quality. False-positive convergence is plausible.

**Fix:** Standard backtracking line-search: try step, accept if loss decreases, otherwise halve. After several successful iterations, attempt to grow step again (Armijo/two-sided rule).

**Developer comment:** Agreed, I was never totally happy with this aspect of the algorithm. It was a quick and dirty way to get this workining initially and it worked well enough that I never bothered to fix it. However, this should be deferred to a future ticket because this is an algorithmic change that needs to be analyzed, which is out of scope for this bug fix ticket.

## Utilities and other

### U-1. `computeNearestPsfMultiBand` projects PSFs onto union bbox (High)

**File:** `python/lsst/meas/extensions/scarlet/utils.py:250-256`

The bbox is built as the union (min/max) of per-band PSF bboxes, and `projectImage` zero-pads bands whose native PSF was smaller. Combined with C-6, different bands' PSFs may originate from different valid sky locations, so the resulting "multiband PSF" mixes per-band PSFs centered at different sky points, with zero-padding hiding the fact that they don't share a pixel.

**Fix:** Companion to C-6: once the search center is fixed across bands, also align the per-band PSF outputs so they share an integer-pixel center before projection.

---

### U-2. Three different "non-zero across bands" idioms (Medium)

**Files:**
- `metrics.py:95` — `model > 0`
- `footprint.py:146` — `np.max(model.data, axis=0) != 0`
- `source.py:150` — `np.any(model.data != 0, axis=0)`

These differ on negative pixels: `> 0` excludes them, `!= 0` includes them, `np.max != 0` agrees with `np.any != 0` only when no negative pixels exist. The "support of a source" question has one correct answer; pick one.

**Fix:** Add a single helper `nonzero_band_support(image)` in `utils.py` and call it from all three sites.

### U-4. `IsolatedSource.__copy__` shares the model array (Medium)

### U-10. No round-trip tests for foundational conversions (Medium)

**Files:** `tests/`

The package has four foundational conversions that everything else depends on:

- `scarletBoxToBBox` ↔ `bboxToScarletBox`
- `afwFootprintToScarlet` ↔ `scarletFootprintToAfw`
- `to_data` ↔ `to_source` (model write/read)
- PSF center handling between LSST `Point2I/Point2D` and scarlet's `Box.origin`

A silent flip in any of these would propagate everywhere. There do not appear to be parameterized round-trip tests for them. This is exactly the kind of gap that lets coordinate-system bugs sit for years.

**Fix:** Add property-style round-trip tests with random/edge-case inputs (negative origins, single-pixel boxes, empty footprints, footprints touching the image edge).

## Cross-Cutting Themes

These are patterns rather than discrete bugs.

1. **Coordinate-system flips are open-coded everywhere.** `(y, x)` vs `(x, y)`, `Box.origin` vs `Point2I`, peak tuples — every conversion is hand-written. The package would benefit from a thin adapter module with named conversions (`yx_to_xy`, `xy_to_yx`, `box_to_xy0`) and the round-trip tests in U-10 to catch silent flips. The most worrying single line is C-10 (`Peak(iy, ix, value)`) — verify before any further changes touch peak handling.

2. **Inconsistent "non-zero across bands" idioms** — see U-2. Three places, three different formulas. Pin down the canonical helper.

3. **NaN/Inf handling is partial.** Recent commits (`0d5d483`, `1603f70`) hardened initialization and the deconvolution model, but the deconvolution loss path (C-11), the variance plane (C-12, DC-2), the chi² aggregation (DB-4), and the `blendedness` metric (U-3) still propagate NaN/Inf silently into the catalog. Worth one focused pass to add `np.isfinite` guards at every boundary that writes into the schema.

4. **Skip-flag semantics are ambiguous in multi-sub-blend cases.** `deblend_skipped` is set on the parent if *any* sub-blend is skipped; sub-flags can be set in parallel for different reasons; multi-peak parents with no intersections can also disappear without any flag at all (C-13). Decide whether parent-level flags mean "any" or "all" and document on the schema fields themselves.

5. **Type hints diverge from runtime types.** `Optional` is missing in several places (U-6, IO-7); `np.array` is used where `np.ndarray` is meant (U-8); `SourceRecord` is annotated where an `int` is passed (DB-9). One pass with `mypy --strict` would surface most of these.

6. **`ScarletDeblendTask` is a god class.** ~1200 LOC class doing six unrelated jobs (DB-8). Splitting it would also reveal a number of state-coupling bugs — the convergence flag inversion (C-1) is plausibly easier to spot when the schema-writing layer is its own class.
